## 2. Core API
- **입력**: 관측 구조체의 필드와 단위(위상이 deg인지 cdeg인지, 거리, 품질), 시간 단위와 랩어라운드 처리
- **호출 방식**: 관측이 올 때만 호출하는지, 관측이 없어도 시간만 넣어 주기적으로 호출해야 하는지. HELD 만료(80/160/240 ms)가 조회 시점에 판정되는지(`uwb_core.c:310-312`)를 알아야 합니다.
- **출력**: `UwbDirection`, `deviation_deg`, origin(OBSERVED/HOLD/BOUNDARY_REFERENCE), quality, 마지막 지지 관측 시각, 태그 상실 판정과 그 기준
- **리셋**: 리셋 API가 있는지, 언제 리셋해야 하는지
- **자원**: double 사용 여부(G474는 단정밀도 FPU), 동적 할당, 스택 사용량, 관측 1회 처리 시간
- **빌드 프로파일**: 실차 시험에 쓸 프로파일. `UWB_V3_ONLY`로 빌드하면 HELD가 나오지 않습니다.

## 3. 위상 부호(−1)와 센터 보정은 어디서 적용하나요
v0.2 §2는 `phase_cdeg`를 "센터 기준, 부호 적용"된 값으로 정의합니다. 그런데 부호는 앵커(`PRODUCT_PDOA_LR_SIGN`)와 Core(`uwb_math.c`) 양쪽에 보입니다.
- 앵커가 보내는 V2 `phase_cdeg`에 부호와 센터 보정이 이미 들어가 있나요? 아니면 Core나 허브가 적용해야 하나요?
- **두 번 적용되면 좌우가 뒤집힙니다.**
- 센터값(연구값 27.231°)이 장착 차량마다 다른 보정값이라면 어디에 저장하나요? 허브가 맡아야 한다면 플래시 설정 필드로 만들겠습니다.

## 4. IF-0 앵커 프레임 (`product_pdoa_can.h` 원본 요청)
허브는 PDoA V2 프레임을 가정하고 있습니다: ID `0x210 + anchor_id`, classic, DLC 8, `0xAC | ver/flags | phase_cdeg i16 | distance_mm u16 | quality_r | seq`.
- `ver_flags`: 버전이 들어가는 니블, b0–b3 플래그의 의미(특히 `R_GATE_PASS`)
- **`seq`**: 측정 1회마다 +1인가요, CAN 송신 1회마다 +1인가요? 허브는 seq로 새 관측인지를 판단하므로 가장 중요한 항목입니다.
- `quality_r`의 정의와 범위
- 앵커가 레거시 거리 프레임(0x20x)도 함께 보내나요?

## 5. 앵커 ID, 비트레이트, 송신 주기
- 단일 PDoA 앵커의 `anchor_id`
- **CAN 비트레이트**: 허브 CAN1은 500 kbps이고, 앵커 제품과 명세는 250 kbps로 알고 있습니다. 서로 다르면 통신이 되지 않습니다.
- 25 Hz CAN 송신은 언제 가능한가요? 지금 프리셋은 CAN 5 Hz로 제한되어 있습니다. 그동안 0x244는 40 ms마다 나가지만 seq는 5 Hz로만 오릅니다.

## 6. 앵커 내부 지연
v0.2의 rf_age는 실제 RF 관측 시각을 기준으로 잡지만, 허브가 아는 시각은 CAN 수신 시각뿐입니다.
- 측정에서 CAN 송신까지 걸리는 지연이 고정인가요, 가변인가요? 대략 몇 ms인가요?
- 고정이면 허브가 설정값으로 보정하겠습니다. 가변이면 IF-0 프레임에 그 값을 실어야 합니다.

## 2차 회신 (UWB 팀, 2026-11-20)

> 1. 이번 시험에서는 UWB_V3_ONLY 빌드 프로파일을 사용합니다. 따라서 src=HELD는 출력되지 않으며, 기존 v0.2의 데이터 구조는 유지하되 해당 상태는 사용하지 않습니다.
> 2. 0x234는 앵커 부팅 시, 1 Hz 주기 및 보정값 변경 시 송신하도록 구현되어 있습니다. 0x234의 유효한 보정 정보를 수신하기 전까지 LAT_VALID=0으로 처리하고, boot_id 또는 보정 세대 변경 시 Core를 리셋하는 방식에 동의합니다. RESTARTED도 시험 기준으로 1초간 유지하면 될 것 같습니다.
> 3. 0x224의 관측 순번은 CAN 송신 횟수가 아닌 RF POLL 교환 기준이며, 관측 경과 시간은 1 ms 단위입니다. 세부 정의와 포화값은 IF-0 명세를 기준으로 공유드리겠습니다.
> 4. Core의 관측당 평균 처리 시간은 PC 환경에서 V3 최소 프로파일 기준 2.829 µs로 측정되었습니다. G474에서의 실제 처리 시간은 아직 측정하지 않았으므로 허브 연동 후 확인 부탁드립니다.

허브 측 정리: HELD는 이번 시험에서 나오지 않음(BBX에 v0.2 §4·§7 반영 요청 필요). 0x234는 부팅·1 Hz·변경 시 송신 → 허브 재부팅 후 1 s 안에 보정값 확보. 0x234 수신 전 LAT_VALID=0, boot_id/보정 세대 변경 시 Core 리셋 + RESTARTED 1 s 합의. 0x224 관측 순번은 RF POLL 기준(새 관측 판단에 사용 가능), 경과 시간 1 ms 단위. G474 처리 시간은 허브에서 측정.

## 3차 회신 (UWB 팀, 2026-11-20) — 요약
- Core: UWB_V3_ONLY 빌드, src=HELD 미출력(v0.2 구조 유지). REFERENCE = 현재 관측 군집 + 이전 판단 참조.
- 0x234: 앵커 부팅 시, 1 s 주기, 보정 정보 변경 시 송신. LAT_VALID=0(보정 수신 전), boot_id/generation 변경 시 Core 리셋 + RESTARTED 1 s 합의.
- boot_id: u8, 부팅마다 MCU UID·내부 타이머 등을 조합해 생성. **충돌 가능**(같은 값이 다시 나올 수 있음).
- generation: 센터 캡처 시작·보정 초기화 시 증가, 보정값 저장 시 유지. CAN에는 하위 16비트.
- 0x224 obs_age: POLL 진단 캡처 직후 → CAN 큐 투입 직전 경과, 1 ms 단위, 0xFE = 254 ms 이상, 0xFF = 유효한 POLL 시각 없음. CAN 중재·전송 지연 미포함.
- 0x224 SN: TAG의 신규 POLL 생성 기준 +1, u8 255→0 순환.
- Core 성능(Windows 로그 재생): 전체 4.585 µs, V3 최소 2.829 µs. G474 미측정.
- 앵커 Classic CAN 500 kbps 적용 완료, 25 Hz PDoA·TWR 관측 시험 중.

허브 반영:
- rf_age = obs_age + (0x244 송신 시각 − 0x224 수신 시각). CAN 전송 지연(500k, 8바이트 약 0.25 ms)은 무시.
- obs_age 0xFE는 "254 ms 이상"이라 하한값으로 쓰고, 0xFF면 해당 관측을 시각 없음으로 처리(rf_age 기준으로 쓰지 않음).
- SN은 새 관측 판단에 사용(같은 SN 재수신은 새 결과 아님).
- boot_id 충돌로 앵커 재부팅을 놓칠 수 있음 → 보조 감지(예: SN 불연속 + CAN1 무수신 구간)를 검토, Core 리셋 여부는 IF-0 명세 확인 후 결정.

## 4차 회신과 자료 전달 (UWB 팀, 2026-11-20)

> 개발 방향 확인했습니다. IF-0 통신 명세와 Core 소스, API 및 연동 예제는 기존 개발 자료를 공유드리겠습니다. 우선 UWB_V3_ONLY 프로파일을 적용하여 0x224/0x234 수신부터 Core 연산 및 0x244 송신까지 기본 데이터 파이프라인을 구현해 주시면 됩니다. 관측 유효성, 중복 데이터, 태그 상실 및 기본적인 재부팅 처리도 반영 부탁드립니다. 재부팅 보조 감지는 우선 1초 통신 단절을 기준으로 적용하고, 세부 임계값은 실차 시험 결과에 따라 조정하면 좋겠습니다. 이번 개발의 우선 목적은 PDoA와 TWR을 결합한 실차 추종 가능성 검증이므로, 기본적인 통신 및 안전성을 확보한 후 실차 시험을 통해 단계적으로 개선하고자 합니다.

전달 자료:
- `docs/IF0_BYTE_CONTRACT_20261120.md`: IF-0 R1 바이트 계약. OBS_RAW 0x224, CAL_STATE 0x234, 수신 측 규칙 §4, 시험 벡터 §6.
- `docs/uwb_core.tar`(SHA-256 `3b83caea…2173f79`): E2 Core. 저장소에는 `App/third_party/uwb_core/`로 수정 없이 반입했고 출처는 `VENDOR.md`에 적음. tar 자체는 커밋하지 않음.

허브 구현 결정(계약 문서가 허브에 맡긴 부분):
- obs_age 0xFE/0xFF: Core에는 추정 시각(수신 시각 − 254 또는 수신 시각)을 넣고, 0x244에는 RF 시각 없음(rf_age 0xFF)으로 보고.
- 복원 시각이 앞 관측보다 이르면 앞 관측 시각으로 맞춤(Core가 역행을 앵커 재시작으로 처리하기 때문).
- 재부팅 보조 감지: OBS 1 s 단절 뒤 복귀, 또는 SN 역행이 3프레임 연속이면 SN 추적·Core 리셋 + RESTARTED.
- LR_SIGN이 3(−1)이 아닌 CAL은 센터로 쓰지 않음(Core가 −1을 고정 적용).
- CAL_STATE 3 s 미수신 시 새 OBS가 없어도 LAT_VALID=0.

## 후속 질문 (허브 구현 검토 후, 2026-11-20)

1. **rf_age 기준 관측**: Core 공개 결과(`UwbTrackingResult`)에는 방향을 실제로 지지한 표본의 RF 시각이 없습니다.
   - 허브는 지금 "마지막으로 수용한 관측"의 시각을 기준으로 씁니다. 이 관측은 Core 창 안에 있지만, 발행한 방향을 지지하지 않을 수도 있습니다.
   - 예: CENTER 표본이 쌓인 뒤 LEFT 쪽 표본이 하나 들어오면, 결과는 CENTER로 유지되면서 rf_age만 짧아집니다.
   - 방향 결정에 쓰인 최신 표본의 tick(또는 SN)을 결과 필드로 노출할 수 있을지 문의드립니다.
2. **재부팅 보조 감지 기준**: 허브는 다음 두 경우를 앵커 재시작으로 봅니다.
